# 长短请求混合时，缓存命中值不值得排队？

本实验使用自行编写的中文客服手册、订单核验记录与问题，按种子生成工单，通过本地 Qwen3 tokenizer 编码。部分工单共用手册，其他工单从第一句起含不同编号。短工单只含一条核验记录，长工单含十四条。每条 prompt 为 46–722 个 token，生成上限为 4–56；实验忽略 EOS 并生成到指定上限。文本是可重复构造的自然语言样本，不含用户工单数据。

固定两张 RTX 4090、每卡 448 MiB KV、相同 guarded 接纳策略。每组 8 个请求同时到达，在 18 和 36 请求/s 两档比较三种路由，每档 300 条，跑三轮，循环轮换执行顺序。least 取未完成请求最少的副本；affinity 允许有前缀命中的副本多排一条；work 把各卡排队和运行中的请求折算成估计工作量，再计入新请求未命中的输入长度。

work 对每个已有请求计入尚未计算的上下文 token，并将剩余生成上限截到 24，每个估计的 decode token 按 16 个输入 token 加权；新请求在该卡命中首块时减去 256 个输入 token。这两个常量是实验用启发式。真实 API 中请求可在 EOS 提前结束，固定长度实验对生成工作量的预测更有利。

```sh
python routing_study.py --model /path/to/Qwen3-0.6B --devices 0 1 --output routing.json
python check_study.py routing.json
```

除最后一列外均取各轮指标的中位数。18 请求/s 时三种策略的达标吞吐接近。36 请求/s 时，考虑 token 工作量后，冷请求等待 P95 较最少请求降低约 26%，代价是减少了前缀命中，达标吞吐也低于缓存亲和的中位数。三种策略在该档都出现严重积压。对于这个流量的低负载服务，简单的最少请求路由已经足够；需要照顾过载时冷请求的尾延迟才有理由试用工作量估计。每组仅三轮，GPU 上存在其他计算进程，结果适用于本次负载和硬件时段。[18 组汇总](routing.json) · [5,400 条逐请求记录](routing.requests.jsonl.gz)
